Data Flow หลัก

Flow: สร้างแผนการปลูก (Rule-Based) 
CreatePlan.tsx (3-step wizard)
  Step 1 → GET /varieties/ → เลือกพันธุ์ข้าว
  Step 2 → เลือกวันเริ่ม (start_date = วันเพาะกล้า/เตรียมดิน)
  Step 3 → ใส่ชื่อแปลง, พื้นที่ (ไร่), ดิน, วิธีปลูก
    → POST /plans/ { variety_id, start_date, area_rai, planting_method, soil_type, plot_name }
    → plans.py router:
        1. query RiceVariety จาก DB
        2. ตรวจ planting_method support
        3. plan_service.generate_plan()
             → คำนวณ actual_planting_date = start_date + PLANTING_DAY[method]
             → if is_photoperiod_sensitive → ตรวจเดือน 7–8
             → _build_tasks() → list[tuple] (day, stage, task_name, desc)
             → calculate_resources() → { seed_kg, fertilizer1_kg, ... }
        4. INSERT PlantingPlan + PlanTask[] ลง PostgreSQL
        5. return PlanResponse
  ← PlansContext.setPlans() → navigate /app/plots
Flow: ถาม RAG Chat 
FloatingChat.tsx
  → POST /chat/ { question, plan_context?, collection?, history[] }
  → chat.py router → rag_service.ask_question()
      → _search(): ค้น ChromaDB ด้วย MMR (k=3, fetch_k=10)
          ถ้าระบุ collection → ค้นใน {collection, general}
          ถ้าไม่ระบุ → ค้นทุก collection
      → สร้าง context = plan_context + เอกสารที่ดึงมา
      → build PromptTemplate + invoke Gemini 2.5 Flash
      → return { answer, sources, model_used, tokens, response_time_ms }
  ← บันทึก ChatHistory (ถ้า logged in)
  ← แสดงคำตอบใน FloatingChat
Flow: Authentication 
Login.tsx
  → POST /auth/login { username, password }  (JSON body ไม่ใช่ form-data)
  → auth.py → verify_password(bcrypt) → create_access_token({ sub, role })
  ← auth.ts: setAuthToken() → localStorage["rice_expert_access_token"]
             decodeJwtPayload() → บันทึก username + role ใน memory

ทุก request ที่ต้อง auth:
  apiFetch(path, opts, requireAuth=true)
    → header: Authorization: Bearer 
    → dependencies.py: get_current_user() → decode JWT → query User จาก DB

Flowchart: กระบวนการสร้างแผนการปลูกข้าว

กระบวนการสร้างแผนการปลูกข้าวของระบบ Rice Expert มีลักษณะเป็น Rule-Based Planning กล่าวคือ ระบบไม่ใช้ AI สร้างแผน แต่ใช้กฎที่กำหนดไว้ตายตัวตามองค์ความรู้ทางการเกษตร เพื่อให้ได้แผนที่แม่นยำและทำซ้ำได้

1
ผู้ใช้เข้าสู่หน้า "สร้างแผน" (CreatePlan.tsx)
ระบบ GET /varieties/ เพื่อโหลดรายการพันธุ์ข้าวจาก PostgreSQL
2
Step 1 — ผู้ใช้เลือกพันธุ์ข้าว
ระบบแสดงพันธุ์ที่ is_active = true ทุกพันธุ์ พร้อมข้อมูล: ชื่อพันธุ์, อายุเก็บเกี่ยว, วิธีปลูกที่รองรับ, ลักษณะพิเศษ (ไวแสง/ไม่ไวแสง)
3
Step 2 — ผู้ใช้เลือกวันเริ่มต้น (start_date)
start_date = วัน Day 0 ของแผน (วันเตรียมดิน/เพาะกล้า) ไม่ใช่วันปลูกจริง
4
Step 3 — ผู้ใช้กรอกรายละเอียดแปลงนา
ชื่อแปลง, พื้นที่ (ไร่), ประเภทดิน (เหนียว/ร่วน/ทราย), วิธีปลูก (นาดำ/นาหว่าน/นาโยน)
5
Backend: คำนวณวันปลูกจริง (actual_planting_date)
actual_planting_date = start_date + PLANTING_DAY[method]
  • นาดำ (transplant) → +25 วัน (รอกล้า 25 วัน)
  • นาหว่าน (broadcast) → +10 วัน (ทำเทือก + แช่เมล็ด)
  • นาโยน (throw) → +15 วัน (รอกล้าถาด 15 วัน)
6
ตรวจสอบเงื่อนไขข้าวไวแสง (Photoperiod Check)
🌙 ถ้า is_photoperiod_sensitive = true:
ตรวจว่า start_date.month ∈ {6, 7} (มิ.ย.–ก.ค.)
❌ ถ้าไม่ใช่ → raise ValueError → HTTP 400 "ข้าวไวต่อช่วงแสงควรเริ่มแผนในช่วงเดือนมิถุนายนถึงกรกฎาคม"
✅ ถ้าใช่ → ผ่าน ดำเนินการต่อ
7
plan_service._build_tasks() — สร้าง Task รายวัน
คำนวณ offset วันของทุก task โดยใช้ระยะการเจริญเติบโตจาก rice_varieties:
  • fert1_day = p + tillering_day (ปุ๋ยครั้งที่ 1 ระยะแตกกอ)
  • fert2_day = p + panicle_initiation_day (ปุ๋ยครั้งที่ 2 ระยะกำเนิดช่อ)
  • heading_abs = p + heading_day (ระยะออกรวง)
  • harvest_abs = p + harvest_age_days (เก็บเกี่ยวตามอายุพันธุ์ นับจากวันปลูกจริง)
  • drain_abs = harvest_abs - 10 (ระบายน้ำก่อนเกี่ยว 10 วัน)
8
plan_service.calculate_resources() — คำนวณปัจจัยการผลิต
คำนวณปริมาณเมล็ดพันธุ์ ปุ๋ย ถาดเพาะกล้า ตามพื้นที่และประเภทดิน
ดินทราย multiplier = 1.2×, ดินร่วน = 1.1×, ดินเหนียว = 1.0×
ปุ๋ยครั้งที่ 1 ใช้สูตรตามประเภทดิน ส่วนปุ๋ยครั้งที่ 2 ใช้ข้อมูลจากพันธุ์ข้าวและคำนวณปริมาณตามพื้นที่/ตัวคูณดิน
9
บันทึกลง PostgreSQL
INSERT planting_plans (1 record) + INSERT plan_tasks (~12–15 records) + resources_snapshot บันทึกเป็น JSON ใน plan
10
ส่ง PlanResponse กลับ → แสดงใน PlotDashboard
Frontend navigate ไป /app/plots → PlansContext โหลดแผนใหม่ → ผู้ใช้เห็นแปลงนาพร้อม task checklist

RAG Pipeline

ระบบ RAG (Retrieval-Augmented Generation) ใช้เพื่อตอบคำถามเกี่ยวกับการปลูกข้าวโดยอิงเอกสารจริง

ขั้นตอนเทคโนโลยีรายละเอียด
IngestionLangChain PyPDFLoader / Docx2txtLoaderโหลดไฟล์ → แบ่ง chunks ด้วย RecursiveCharacterTextSplitter
Embeddinggemini-embedding-001แปลง chunk text → vector (float array)
StorageChromaDB (local persist ./chroma_db)collections แยกตามพันธุ์ข้าว + general
RetrievalMMR (Maximal Marginal Relevance)k=3 chunks, fetch_k=10 → เลือกที่หลากหลาย ลด redundancy
Generationgemini-2.5-flash (temperature=0.3)ตอบเป็นภาษาไทย ≤5 ประโยค

Chunk Parameters: chunk_size=500, chunk_overlap=50 — ตั้งค่าผ่าน .env สำหรับ experiment
Multi-Collection Strategy: ค้นใน collection เฉพาะพันธุ์ + general เสมอ เพื่อให้ได้ทั้งข้อมูลเฉพาะและความรู้ทั่วไป
Deduplication: ใช้ page_content[:80] เป็น key กรอง chunk ซ้ำออก ก่อนส่งให้ LLM

Plan Generation Logic — รายละเอียดกฎการสร้างแผน

กฎการสร้างแผนทั้งหมดอยู่ใน plan_service.py ไม่ใช้ AI — ทุกอย่างคำนวณจาก offset arithmetic

สูตรคำนวณวันสำคัญ

p = PLANTING_DAY[method]          # offset วันปลูกจากวันเริ่ม
fert1_day = p + tillering_day      # วันใส่ปุ๋ยครั้งที่ 1 (ระยะแตกกอ)
fert2_day = p + panicle_day        # วันใส่ปุ๋ยครั้งที่ 2 (กำเนิดช่อ)
heading   = p + heading_day        # วันออกรวง
harvest   = p + harvest_age_days   # วันเก็บเกี่ยว นับจากวันปลูกจริง
drain     = harvest - 10           # วันระบายน้ำก่อนเก็บเกี่ยว 10 วัน

ตัวอย่าง: ขาวดอกมะลิ 105 — นาดำ — 2 ไร่ — ดินเหนียว

5. สร้างแผนปลูก (CreatePlan) — Wizard 3 ขั้นตอน

URL /app/create-plan — ฟอร์มแบ่งเป็น 3 ขั้นตอน มี stepper ด้านบนให้เห็นว่าอยู่ขั้นไหน

1
Step 1 — เลือกพันธุ์ข้าว
• ช่องค้นหาด้านบน (ค้นจากชื่อพันธุ์)
• Grid card พันธุ์ข้าว: ชื่อ + badge "ไวแสง / ไม่ไวแสง" + แสดงวิธีปลูกที่รองรับ
• คลิก card → ✓ checkmark + ขอบเขียว → ปุ่ม "ถัดไป" เปิดใช้งาน
2
Step 2 — เลือกวันเริ่มเตรียมงาน (start_date)
• ปฏิทินเลือกวันแบบ react-day-picker ภาษาไทย
• วันที่ผ่านมาแล้วจะกดไม่ได้ (disabled)
• ถ้าพันธุ์ไวแสง → disabled ทุกเดือนยกเว้น มิ.ย.–ก.ค. + แสดงกล่อง warning สีเหลือง
• start_date คือวัน Day 0 ของแผน (วันเตรียมดิน) ไม่ใช่วันปลูกจริง
3
Step 3 — รายละเอียดแปลง
• ชื่อแปลง: ตั้งชื่อเรียกแปลง เช่น "แปลงหลังบ้าน"
• พื้นที่ (ไร่): ตัวเลข ละเอียด 0.1 ไร่
• ประเภทดิน: 3 ปุ่ม (ดินเหนียว / ดินร่วน / ดินทราย) พร้อมสูตรปุ๋ยที่เหมาะ
• วิธีปลูก: แสดงเฉพาะวิธีที่พันธุ์ที่เลือกรองรับ (นาดำ/นาหว่าน/นาโยน)

1. สร้าง Admin คนแรก (First-time Setup)

ครั้งแรกที่ติดตั้งระบบ ยังไม่มี admin คนใดเลย → endpoint /admin/* ล็อกเข้าไม่ได้ ต้องเข้าฐานข้อมูลโดยตรง:

-- 1. สมัคร user ปกติผ่านหน้าเว็บก่อน (role="user")
-- 2. เข้า psql / pgAdmin เชื่อม DB "ricerag"
UPDATE users SET role = 'admin' WHERE username = 'your_username';

-- 3. Logout + Login ใหม่ → JWT จะมี role="admin"
-- 4. เมนู "จัดการระบบ" จะปรากฏใน sidebar

หลังจากมี admin คนแรกแล้ว สามารถเปลี่ยน role คนอื่นผ่าน UI (แท็บ "ผู้ใช้") ได้เลย ไม่ต้องแก้ SQL อีก

2. แท็บ "ผู้ใช้" — จัดการ Role

  1. คลิกแท็บ ผู้ใช้ → ตารางรายชื่อทั้งหมด (username, role, วันที่สมัคร)
  2. คอลัมน์ "role" มี dropdown: User / Admin
  3. เปลี่ยนค่าใน dropdown → PUT /admin/users/{id}/role → อัปเดตทันที

ข้อจำกัด: admin ห้าม downgrade role ของตัวเอง เป็น user (ป้องกันระบบไม่มี admin เหลือ) — ระบบจะ return error 400 ถ้าพยายามทำ

6. แท็บ "ช่องว่างความรู้" (Gap Detector) — วิเคราะห์คำถามที่ฐานความรู้อาจยังไม่ครอบคลุม

Feedback loop ช่วยให้ admin รู้ว่าต้อง อัปโหลดเอกสารเรื่องอะไรเพิ่ม โดยอิงจากพฤติกรรมการถามจริงของผู้ใช้ ไม่ต้องเดาเอง

เกณฑ์กรอง (SQL filter)ความหมาย
chunks_retrieved = 0ไม่มี chunk ใดใน ChromaDB แตะคำถามนี้ (relevance ต่ำมาก) — เอกสารไม่ครอบคลุม
answer ILIKE '%ไม่ทราบ%'เงื่อนไข endpoint ปัจจุบันสำหรับคำตอบที่ระบุว่าไม่ทราบ ทั้งนี้ prompt ล่าสุดอาจตอบคำแนะนำทั่วไปพร้อมหมายเหตุเมื่อไม่พบคำตอบตรงในเอกสาร
-- GET /admin/gaps
SELECT question, COUNT(id) AS count, MAX(created_at) AS last_asked_at
FROM chat_history
WHERE chunks_retrieved = 0 OR answer ILIKE '%ไม่ทราบ%'
GROUP BY question
ORDER BY count DESC
LIMIT 20;

วิธีใช้: admin เปิดแท็บนี้เพื่อดูรายการคำถามที่ระบบตอบไม่ได้ (พร้อมจำนวนครั้งที่ถาม + วันล่าสุด) → สรุปหัวข้อที่ถามบ่อย → ไปแท็บ "เอกสาร" อัปโหลด PDF/คู่มือเรื่องนั้นเข้า collection ที่เหมาะสม → รอ embedding → ครั้งถัดไป AI จะตอบได้

🔧 ปัญหาที่พบบ่อย (Troubleshooting)

ล็อกอินไม่ได้ — error "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"
  • ตรวจสอบ Caps Lock / ภาษาคีย์บอร์ด (EN)
  • ถ้าลืมรหัสผ่าน → ปัจจุบันระบบยังไม่มี "ลืมรหัสผ่าน" — ต้อง admin แก้ใน DB ด้วย UPDATE users SET hashed_password = ... (ใช้ bcrypt hash)
  • ถ้าพิมพ์ถูกแต่ยังผิด → ลองสมัครใหม่ หรือตรวจว่า backend ทำงานอยู่ (http://localhost:8000/docs)
สร้างแผนไม่ได้ — error "ข้าวไวต่อช่วงแสงควรเริ่มแผนในช่วงเดือน มิ.ย. – ก.ค."

พันธุ์ที่เลือกเป็นข้าวไวแสง (photoperiod-sensitive) ระบบกำหนดให้เริ่มแผนในเดือน มิ.ย.–ก.ค. เพื่อให้วันปลูกจริงและช่วงออกดอก/เก็บเกี่ยวสัมพันธ์กับฤดูกาล วิธีแก้:

  • เลือกวันเริ่มแผนในเดือน มิ.ย. หรือ ก.ค. แล้วสร้างแผนใหม่
  • เลือกพันธุ์ไม่ไวแสงแทน (เช่น กข43) ซึ่งปลูกได้ตลอดปี
AI แชทตอบไม่ตรงคำถาม / มีหมายเหตุว่าใช้ความรู้ทั่วไป
  • ข้อมูลไม่อยู่ในคลัง: ระบบใช้เอกสารที่ admin อัปโหลดเป็นหลัก หากไม่มีคำตอบตรง ระบบอาจให้คำแนะนำทั่วไปพร้อมหมายเหตุว่าไม่พบในเอกสารอ้างอิง
    → admin ต้องอัปโหลดเอกสารเพิ่มในแท็บ "เอกสาร" → เลือก collection ที่เหมาะ
  • คำถามคลุมเครือ: ระบุพันธุ์ข้าว / ระยะ / ปัญหาให้ชัด
  • ลองเปลี่ยน collection: ถ้าอยู่ในหน้า Landing (guest) → ระบบค้นทุก collection / ใน PlotDashboard → ค้นเฉพาะ collection ของพันธุ์ + general
อัปโหลดเอกสารแล้ว AI ยังไม่รู้
  • รอสักครู่ — embedding process อาจใช้เวลา 5–30 วินาทีขึ้นอยู่กับขนาดไฟล์

3.1 ภาพรวมสถาปัตยกรรมระบบ (System Architecture)

ระบบได้รับการออกแบบตามรูปแบบสถาปัตยกรรม Client-Server แบบ 3 ชั้น (Three-Tier Architecture) โดยแบ่งความรับผิดชอบของแต่ละชั้นออกจากกันอย่างชัดเจน เพื่อให้ระบบมีความยืดหยุ่น บำรุงรักษาได้ง่าย และสามารถขยายขีดความสามารถได้ในอนาคต

ชั้นที่ 1 — Presentation Layer (หน้าบ้าน): พัฒนาด้วย React 18 ร่วมกับ Vite 6 เป็น build tool และ TypeScript เพื่อเพิ่มความปลอดภัยของชนิดข้อมูล จัดการ UI ด้วย Tailwind CSS 4 และ Radix UI สำหรับ component ระดับ accessibility ส่วนการจัดการ state ภายในใช้ React Context API (PlansContext) เพื่อแชร์สถานะแผนปลูกทั่วทั้งแอปพลิเคชัน ชั้นนี้ทำหน้าที่รับข้อมูลจากผู้ใช้ แสดงผลลัพธ์ และส่งคำขอ HTTP ไปยัง API Layer ผ่าน apiFetch() utility function

ชั้นที่ 2 — Application Layer (หลังบ้าน): พัฒนาด้วย FastAPI framework บน Python ทำหน้าที่เป็น REST API server ที่รับฟังที่พอร์ต 8000 ชั้นนี้ประกอบด้วย router 7 กลุ่ม (auth, chat, documents, plans, prompts, varieties, admin) ซึ่งแต่ละกลุ่มรับผิดชอบฟีเจอร์เฉพาะด้าน การตรวจสอบสิทธิ์ใช้ JWT (JSON Web Token) มาตรฐาน HS256 ผ่านไลบรารี python-jose และ passlib สำหรับ bcrypt password hashing การ serialize/deserialize ข้อมูลใช้ Pydantic เพื่อให้มั่นใจว่า request และ response มีรูปแบบถูกต้องเสมอ Business logic หลักแบ่งเป็น 2 service คือ plan_service.py สำหรับการสร้างแผนปลูกแบบ Rule-Based และ rag_service.py สำหรับ RAG pipeline การเชื่อมต่อฐานข้อมูลเชิงสัมพันธ์ใช้ SQLAlchemy 2.0 ORM และการเชื่อมต่อ LLM ใช้ LangChain เป็น framework กลาง

ชั้นที่ 3 — Data Layer: ระบบใช้ฐานข้อมูล 2 ประเภทแยกกันตามหน้าที่ ได้แก่ PostgreSQL ที่เชื่อมต่อผ่านค่า DATABASE_URL สำหรับข้อมูลเชิงสัมพันธ์ทั้งหมด เช่น ข้อมูลผู้ใช้ แผนการปลูก งานในแผน และประวัติการสนทนา และ ChromaDB สำหรับจัดเก็บ vector embeddings ของเอกสารความรู้เพื่อใช้ค้นหาเชิงความหมาย (semantic search) เท่านั้น การสื่อสารกับ Google Gemini API ใช้ผ่าน langchain-google-genai โดยใช้โมเดล gemini-2.5-flash สำหรับการสร้างคำตอบ และ gemini-embedding-001 สำหรับการสร้าง vector embeddings

ระบบกำหนดระดับสิทธิ์การเข้าถึง (Access Level) ออกเป็น 3 ระดับ เพื่อควบคุมการใช้งานฟีเจอร์ต่าง ๆ ให้เหมาะสมกับบทบาทของผู้ใช้แต่ละกลุ่ม ดังนี้

ระดับที่ 1 — ผู้เยี่ยมชม (Guest): ผู้ใช้ที่ยังไม่ได้เข้าสู่ระบบสามารถเข้าถึงหน้าแรก (Landing Page) เพื่อทดลองใช้งานระบบแชทถาม-ตอบเบื้องต้นและเรียกดูรายการเอกสารความรู้ที่แสดงบนหน้าแรก อย่างไรก็ตาม การสนทนาของผู้เยี่ยมชมจะไม่ถูกบันทึกลงฐานข้อมูล

ระดับที่ 2 — ผู้ใช้งานทั่วไป (User): ผู้ใช้ที่ผ่านการลงทะเบียนและเข้าสู่ระบบแล้วสามารถใช้งานฟีเจอร์ครบถ้วน ได้แก่ การสร้างและจัดการแผนการปลูกข้าว การติดตามงานผ่านปฏิทิน การแก้ไข โคลน และพิมพ์แผน รวมถึงการใช้งาน AI แชทผู้เชี่ยวชาญพร้อมบันทึกประวัติการสนทนา

ระดับที่ 3 — ผู้ดูแลระบบ (Admin): มีสิทธิ์เพิ่มเติมในการบริหารจัดการระบบ ได้แก่ การอัปโหลดและลบเอกสารความรู้เข้า ChromaDB การจัดการพันธุ์ข้าว (CRUD) การจัดการ Prompt Templates และ FAQ การจัดการบทบาทของผู้ใช้ และการเรียกดูรายงานช่องว่างความรู้ (Gap Detector) การเลื่อนระดับเป็น Admin ครั้งแรกต้องแก้ไขฐานข้อมูลโดยตรง หลังจากนั้น Admin สามารถเปลี่ยนบทบาทผู้ใช้รายอื่นได้ผ่าน endpoint PUT /admin/users/{id}/role

3.3 การออกแบบฐานข้อมูล (Database Design)

ระบบใช้กลยุทธ์การจัดเก็บข้อมูลแบบ Polyglot Persistence โดยเลือกใช้ฐานข้อมูล 2 ประเภทที่มีลักษณะเฉพาะต่างกันอย่างชัดเจน เพื่อให้แต่ละส่วนของระบบทำงานได้อย่างมีประสิทธิภาพสูงสุด

PostgreSQL — ฐานข้อมูลเชิงสัมพันธ์ (Relational Database)

ใช้สำหรับจัดเก็บข้อมูลที่มีความสัมพันธ์กัน ต้องการความถูกต้องของธุรกรรม (ACID compliance) และข้อมูลที่มีโครงสร้างชัดเจน ระบบออกแบบตาราง 7 ตารางโดยใช้ UUID เป็น Primary Key ทุกตาราง เพื่อหลีกเลี่ยงการชนกันของ ID เมื่อระบบขยายขนาด รายละเอียดแต่ละตารางจะนำเสนอในรูปแบบตารางในหัวข้อถัดไป ความสัมพันธ์หลักระหว่างตารางมีดังนี้

  • ตาราง users มีความสัมพันธ์แบบ One-to-Many กับ planting_plans — ผู้ใช้หนึ่งคนมีแผนการปลูกได้หลายแผน
  • ตาราง planting_plans มีความสัมพันธ์แบบ One-to-Many กับ plan_tasks — แต่ละแผนมีงานย่อย 12–15 รายการ โดยกำหนด CASCADE DELETE เพื่อให้งานถูกลบตามเมื่อลบแผน
  • ตาราง users มีความสัมพันธ์แบบ One-to-Many กับ chat_history — บันทึกประวัติการสนทนาพร้อม metrics ทดลองครบถ้วน
  • ฟิลด์ rice_varieties.collection_name เชื่อมโยงกับ documents.chroma_collection เพื่อระบุว่าเอกสารชิ้นใดอยู่ใน ChromaDB collection ใด

ตาราง planting_plans บันทึก resources_snapshot เป็น JSON field ณ เวลาที่สร้างแผน เพื่อให้ข้อมูลปัจจัยการผลิต (เมล็ดพันธุ์ ปุ๋ย) คงที่แม้จะมีการแก้ไขสูตรพันธุ์ข้าวในภายหลัง นอกจากนี้ยังบันทึก variety_name เป็น snapshot เพื่อป้องกันข้อมูลสูญหายหากพันธุ์ข้าวถูกลบออกจากระบบ

ChromaDB — ฐานข้อมูล Vector (Vector Database)

ใช้สำหรับจัดเก็บ vector embeddings ของเนื้อหาเอกสารความรู้โดยเฉพาะ ไม่ได้ใช้จัดเก็บข้อมูลสถานะของระบบ ChromaDB จัดระเบียบข้อมูลเป็น collection โดยแต่ละ collection ตรงกับพันธุ์ข้าว 1 พันธุ์ บวก collection general สำหรับเอกสารทั่วไป ข้อมูลที่จัดเก็บต่อ 1 chunk ประกอบด้วย vector embedding จาก gemini-embedding-001, เนื้อหาข้อความต้นฉบับ และ metadata เช่น ชื่อไฟล์ต้นทางและหมายเลขหน้า ไฟล์ทั้งหมดถูก persist ลงดิสก์ที่ไดเรกทอรี ./chroma_db/ ในรูปแบบ SQLite

3.4.1 ระบบยืนยันตัวตนและจัดการสิทธิ์ (Authentication and Authorization)

ระบบใช้กลไกยืนยันตัวตนด้วย JSON Web Token (JWT) มาตรฐาน HS256 ผ่านไลบรารี python-jose และการเข้ารหัสรหัสผ่านด้วย bcrypt ผ่านไลบรารี passlib ทุก endpoint ที่ต้องการการยืนยันตัวตนจะตรวจสอบ token ผ่าน FastAPI dependency injection ก่อนอนุญาตให้ประมวลผล

การสมัครสมาชิก (Register): Frontend ส่ง HTTP POST ไปยัง /auth/register พร้อม JSON body ประกอบด้วย username และ password Backend ตรวจสอบว่า username ซ้ำกับที่มีอยู่ในตาราง users หรือไม่ หากซ้ำจะปฏิเสธด้วย HTTP 400 พร้อมข้อความแจ้งเตือนภาษาไทย หากผ่าน ระบบเรียก hash_password() ซึ่งใช้ bcrypt แปลง plain text password เป็น hashed string ที่ไม่สามารถย้อนกลับได้ จากนั้น INSERT record ลงตาราง users โดยกำหนด role = "user" เป็นค่าเริ่มต้นสำหรับผู้ใช้ทั่วไปทุกคน

การเข้าสู่ระบบ (Login): Frontend ส่ง HTTP POST ไปยัง /auth/login พร้อม JSON body ประกอบด้วย username และ password (ไม่ใช่ form-data) Backend Query ตาราง users ด้วย username จากนั้นเรียก verify_password(plain, hashed) ซึ่ง bcrypt เปรียบเทียบรหัสผ่านที่รับมากับ hashed password ใน DB หากไม่ตรงจะปฏิเสธด้วย HTTP 401 หากผ่าน ระบบเรียก create_access_token({"sub": username, "role": role}) ซึ่งสร้าง JWT โดย encode payload พร้อมกำหนดวันหมดอายุ ACCESS_TOKEN_EXPIRE_MINUTES = 1440 (24 ชั่วโมง) และลงนามด้วย SECRET_KEY จาก environment variable ส่ง token กลับเป็น JSON

การจัดเก็บ Token ฝั่ง Frontend: lib/auth.ts รับ token แล้วบันทึกลง localStorage ที่ key rice_expert_access_token พร้อมกัน Frontend ถอดรหัส JWT payload ด้วย decodeJwtPayload() (base64 decode เฉพาะส่วน payload) เพื่อดึง username และ role บันทึกลง localStorage เพิ่มเติม การ decode นี้ทำฝั่ง client เท่านั้น ไม่มี endpoint /me แยกต่างหาก

การตรวจสอบสิทธิ์ทุก Request: ทุก endpoint ที่ต้องการ auth จะรับ current_user ผ่าน FastAPI dependency โดยมี 3 ระดับ ได้แก่ get_current_user() สำหรับ endpoint ที่บังคับ login (ถ้าไม่มี token จะปฏิเสธ HTTP 401), get_optional_user() สำหรับ endpoint ที่รองรับทั้ง guest และ logged-in user (เช่น chat) และ require_admin() สำหรับ endpoint ที่บังคับ role = "admin" (ถ้าไม่ใช่ admin จะปฏิเสธ HTTP 403) โดย dependency ทั้งหมดดึง token จาก Authorization: Bearer <token> header ถอดรหัสด้วย decode_access_token() และ Query ตาราง users เพื่อให้ได้ User object ที่พร้อมใช้งาน

3.4.2 ระบบจัดการแผนการปลูกแบบ Rule-Based

ระบบสร้างแผนการปลูกข้าวโดยอาศัย กฎที่กำหนดตายตัวตามองค์ความรู้ทางการเกษตร ไม่ใช้ AI หรือโมเดลภาษาในการสร้างแผนแต่อย่างใด เพื่อให้ได้แผนที่มีความแม่นยำ ตรวจสอบได้ และทำซ้ำได้ในทุกครั้ง

การคำนวณวันปลูกจริง (Actual Planting Date): ผู้ใช้กำหนด start_date ซึ่งหมายถึง Day 0 ของแผน (วันเริ่มเตรียมดินหรือเพาะกล้า) ระบบจะคำนวณวันปลูกจริงโดยบวก offset วันตามวิธีการปลูก ดังนี้

  • นาดำ (transplant): actual_planting_date = start_date + 25 วัน (ระยะรอให้กล้าโต)
  • นาหว่าน (broadcast): actual_planting_date = start_date + 10 วัน (ระยะทำเทือกและแช่เมล็ด)
  • นาโยน (throw): actual_planting_date = start_date + 15 วัน (ระยะรอกล้าถาด)

การตรวจสอบเงื่อนไขข้าวไวแสง (Photoperiod Validation): หากพันธุ์ข้าวที่เลือกมีคุณสมบัติ is_photoperiod_sensitive = true ระบบจะตรวจสอบว่าเดือนของ start_date อยู่ในช่วงเดือนมิถุนายนหรือกรกฎาคมเท่านั้น หากไม่เป็นไปตามเงื่อนไข ระบบจะปฏิเสธการสร้างแผนและส่งข้อผิดพลาด HTTP 400 พร้อมข้อความแจ้งเตือนเป็นภาษาไทย ทั้งนี้ actual_planting_date ยังคงถูกคำนวณจาก start_date + PLANTING_DAY[method] เพื่อใช้แสดง/ส่งกลับใน response

การสร้างงานรายวัน (Task Generation): plan_service._build_tasks() คำนวณ offset วันของงานทุกรายการโดยใช้ระยะการเจริญเติบโตที่บันทึกไว้ในตาราง rice_varieties สูตรคำนวณหลักคือ

  • ปุ๋ยครั้งที่ 1: fert1_day = p + tillering_day (ระยะแตกกอ)
  • ปุ๋ยครั้งที่ 2: fert2_day = p + panicle_initiation_day (ระยะกำเนิดช่อดอก)
  • ระยะออกรวง: heading_abs = p + heading_day
  • วันเก็บเกี่ยว: harvest_abs = p + harvest_age_days
  • วันระบายน้ำ: drain_abs = harvest_abs - 10

โดย p หมายถึง offset วันปลูกจริงจาก start_date โค้ดมี safety net สำหรับกรณีที่รายการงานเริ่มก่อน Day 0 โดยจะปรับ offset ของงานให้เริ่มที่ Day 0 และปรับ actual_planting_date ให้สอดคล้องกัน แต่ไม่ได้แก้ค่า start_date ที่ผู้ใช้เลือก

การคำนวณปัจจัยการผลิต (Resource Calculation): plan_service.calculate_resources() คำนวณปริมาณเมล็ดพันธุ์และปุ๋ยตามพื้นที่และประเภทดิน โดยใช้ soil multiplier ได้แก่ ดินเหนียว 1.0×, ดินร่วน 1.1× และดินทราย 1.2× อัตราเมล็ดพันธุ์กำหนดตามวิธีปลูก ได้แก่ นาดำ 5 กก./ไร่, นาหว่าน 15 กก./ไร่ และนาโยน 6 กก./ไร่ พร้อมถาดเพาะ 50 ถาด/ไร่ ผลการคำนวณบันทึกเป็น JSON ใน resources_snapshot ณ เวลาที่สร้างแผน ทั้งนี้ปุ๋ยครั้งที่ 1 ใช้สูตรตามประเภทดิน ส่วนปุ๋ยครั้งที่ 2 ใช้ข้อมูลของพันธุ์ข้าวและคำนวณปริมาณตามพื้นที่/ตัวคูณดิน

Flow การสร้างแผนแบบครบวงจร (Create Plan End-to-End): Frontend นำเสนอ wizard 3 ขั้นตอน ได้แก่ ขั้นที่ 1 ดึงรายการพันธุ์ข้าวด้วย GET /varieties/ และให้ผู้ใช้เลือก ขั้นที่ 2 เลือก start_date ผ่าน date picker และขั้นที่ 3 กรอกชื่อแปลง พื้นที่ ประเภทดิน และวิธีปลูก เมื่อกด "สร้างแผน" Frontend ส่ง HTTP POST ไปยัง /plans/ พร้อม JWT token Backend ตรวจสอบว่าพันธุ์ข้าวมีอยู่และ is_active = true ตรวจสอบว่าวิธีปลูกที่เลือกอยู่ใน supported_methods ของพันธุ์นั้น จากนั้นส่งข้อมูลทั้งหมดไปยัง plan_service.generate_plan() ซึ่งคืนค่า tasks, resources และ actual_planting_date ระบบ INSERT PlantingPlan 1 record ลง PostgreSQL ด้วย db.flush() เพื่อให้ได้ plan.id ก่อน จากนั้นวนลูป INSERT PlanTask ทุกรายการโดยอ้างอิง plan_id นั้น เรียก db.commit() ครั้งเดียวเพื่อ atomic transaction สุดท้ายส่ง PlanResponse กลับ Frontend ซึ่ง PlansContext จะเพิ่มแผนใหม่เข้า state และ navigate ไปหน้า Plots

การแก้ไขแผน (Update Plan): Frontend ส่ง HTTP PATCH ไปยัง /plans/{plan_id} โดยแก้ไขได้เฉพาะ 3 field ได้แก่ plot_name, area_rai และ soil_type ไม่สามารถแก้ไขพันธุ์ข้าว วิธีปลูก หรือวันเริ่มต้นได้ เพื่อรักษา task timeline ที่คำนวณไว้แล้ว Backend ตรวจสอบ ownership ว่า plan.user_id == current_user.id หาก area_rai หรือ soil_type มีการเปลี่ยนแปลง ระบบคำนวณ resources_snapshot ใหม่ทันที โดยมีกฎว่า หากเปลี่ยนประเภทดิน สูตรปุ๋ยจะใช้ default ตามดินใหม่แทนสูตรของพันธุ์เดิม เพื่อให้คำแนะนำตรงกับสภาพดินที่เปลี่ยนไป task ทุกรายการคงเดิมโดยไม่คำนวณใหม่เพื่อรักษา progress ที่ทำไปแล้ว

การโคลนแผน (Clone Plan): Frontend ส่ง HTTP POST ไปยัง /plans/{plan_id}/clone พร้อมระบุเฉพาะ start_date ใหม่ Backend ดึงแผนต้นฉบับและตรวจสอบ ownership จากนั้นเรียก plan_service.generate_plan() ด้วยพารามิเตอร์เดิมทั้งหมด (พันธุ์ วิธีปลูก พื้นที่ ดิน) แต่ใช้ start_date ใหม่ที่รับมา ผลลัพธ์คือแผนใหม่ที่มี tasks คำนวณตามวันใหม่ทั้งหมด ชื่อแปลงจะต่อท้ายด้วย "(สำเนา)" โดยอัตโนมัติหากไม่ระบุชื่อใหม่ แผนโคลนเป็น record แยกต่างหากจากแผนต้นฉบับโดยสมบูรณ์

การ Toggle Task (บันทึกความคืบหน้า): Frontend ส่ง HTTP PATCH ไปยัง /plans/{plan_id}/tasks/{task_id}/toggle Backend ตรวจสอบ ownership ของแผนก่อน จากนั้นสลับค่า task.is_completed = not task.is_completed และ commit ทันที ส่ง PlanTaskResponse กลับพร้อมสถานะใหม่ PlansContext อัปเดต task ใน state โดยไม่ต้อง reload แผนทั้งหมด

การลบแผน (Delete Plan): Frontend ส่ง HTTP DELETE ไปยัง /plans/{plan_id} Backend ตรวจสอบ ownership จากนั้นลบ PlanTask ทุกรายการของแผนนั้นด้วย query DELETE แล้วจึงลบ PlantingPlan record และเรียก db.commit() ครั้งเดียว โครงสร้าง FK ของ plan_tasks.plan_id มี ondelete="CASCADE" เป็นการรองรับระดับฐานข้อมูล แต่ implementation ปัจจุบันลบ tasks โดยตรงก่อนลบ plan

3.4.3 ระบบตอบคำถามอัจฉริยะด้วยเทคนิค RAG (Retrieval-Augmented Generation Pipeline)

ระบบตอบคำถามใช้เทคนิค Retrieval-Augmented Generation (RAG) ตามแนวทางของ Lewis et al. (2020) ซึ่งผสานการค้นหาเอกสารเชิงความหมายเข้ากับความสามารถของ Large Language Model เพื่อให้คำตอบที่อ้างอิงจากเอกสารความรู้จริง แทนที่จะตอบจากความรู้ภายในโมเดลเพียงอย่างเดียว กระบวนการทำงานของระบบ RAG แบ่งออกเป็น 2 Phase ที่เกิดขึ้นในเวลาต่างกัน ได้แก่ Phase การนำเข้าเอกสาร (Offline Ingestion) และ Phase การตอบคำถาม (Online Retrieval)

Phase 1 — การนำเข้าและประมวลผลเอกสาร (Document Ingestion)

Phase นี้เกิดขึ้นเมื่อ Admin อัปโหลดเอกสารความรู้ใหม่เข้าระบบผ่าน Admin Panel โดยมีขั้นตอนดังนี้

ขั้นตอนที่ 1 — ตรวจสอบสิทธิ์และรับไฟล์: Frontend ส่ง HTTP POST ไปยัง /documents/upload เป็น multipart/form-data พร้อมแนบ JWT token ใน Authorization header Backend ตรวจสอบสิทธิ์ผ่าน require_admin dependency ซึ่งถอดรหัส JWT และตรวจสอบว่า user.role == "admin" หากไม่ผ่านจะปฏิเสธด้วย HTTP 403 จากนั้นตรวจสอบว่า collection ที่ระบุอยู่ในชุด collection_name ของตาราง rice_varieties ทั้งหมด หรือเป็น collection พิเศษ general และตรวจสอบนามสกุลไฟล์ว่าเป็น .pdf, .txt หรือ .docx เท่านั้น ก่อนบันทึกไฟล์ต้นฉบับลงดิสก์ที่ ./uploads/{collection}/{filename}

ขั้นตอนที่ 2 — โหลดเนื้อหาด้วย Document Loader: rag_service.ingest_document() เลือก Document Loader ตามนามสกุลไฟล์ ได้แก่ PyPDFLoader สำหรับ .pdf ซึ่งอ่านทีละหน้าและแนบ metadata หมายเลขหน้า, Docx2txtLoader สำหรับ .docx ที่แปลง Word เป็น plain text และ TextLoader สำหรับ .txt ผลลัพธ์คือ list[Document] ซึ่งแต่ละ object ประกอบด้วย page_content (ข้อความ) และ metadata ที่ระบุ source path และหมายเลขหน้า ณ จุดนี้ยังไม่มีการ embed แต่อย่างใด

ขั้นตอนที่ 3 — ตัดแบ่งเป็น Chunks: RecursiveCharacterTextSplitter ตัดแบ่งเนื้อหาโดยกำหนด chunk_size=500 และ chunk_overlap=50 อัลกอริทึมพยายามตัดตามตัวคั่นตามลำดับ ได้แก่ \n\n, \n, และตัวอักษร เพื่อให้แต่ละ chunk จบที่จุดที่มีความหมายสมบูรณ์ที่สุด ค่า chunk_overlap=50 ทำให้แต่ละ chunk ซ้อนทับกับ chunk ถัดไป 50 ตัวอักษร เพื่อป้องกันข้อมูลสำคัญถูกตัดขาดที่รอยต่อ ค่า chunk_size=500 เหมาะสมสำหรับเอกสารคู่มือการเกษตรภาษาไทยที่มีลักษณะอธิบายแต่ละหัวข้อแยกจากกันชัดเจน

ขั้นตอนที่ 4 — สร้าง Vector Embeddings และบันทึกลง ChromaDB: Chroma.add_documents(chunks) เรียก Google Gemini Embedding API (gemini-embedding-001) เพื่อแปลงข้อความของแต่ละ chunk เป็น vector embedding ซึ่งแทนความหมายเชิงความหมาย (semantic meaning) ของข้อความนั้น ChromaDB บันทึก 3 ส่วนต่อ chunk ได้แก่ vector embedding, ข้อความต้นฉบับ และ metadata (source path, หน้า) ลงดิสก์ที่ ./chroma_db/ ทันที การส่งคำขอ embedding ถูกจัดการผ่าน LangChain/Chroma ตามจำนวน chunks และการ batch ภายในไลบรารี

ขั้นตอนที่ 5 — บันทึก Metadata ลง PostgreSQL: หลังจาก embedding สำเร็จ ระบบ INSERT record ลงตาราง documents ใน PostgreSQL บันทึกชื่อไฟล์ path ของไฟล์ต้นฉบับ ชื่อ collection และ UUID ของ admin ที่อัปโหลด ตาราง documents ทำหน้าที่เป็น catalog สำหรับแสดงรายการเอกสารและใช้อ้างอิงเมื่อต้องลบเอกสารออกจากระบบ ทั้งนี้เนื้อหาจริงและ vectors อยู่ใน ChromaDB ไม่ใช่ PostgreSQL ผลลัพธ์สุดท้ายคือเอกสารพร้อมใช้งานใน RAG pipeline ทันทีโดยไม่ต้อง restart server

Phase 2 — การตอบคำถาม (Online Retrieval and Generation)

Phase นี้เกิดขึ้นทุกครั้งที่ผู้ใช้ที่ล็อกอินส่งคำถามผ่าน FloatingChat widget ซึ่งปรากฏอยู่ในทุกหน้าภายใน protected app (/app/*) ส่วนผู้เยี่ยมชมใช้ chat ที่อยู่บนหน้า Landing แยกต่างหาก

ขั้นตอนที่ 1 — เตรียม Request ฝั่ง Frontend: FloatingChat.tsx รับข้อความจากผู้ใช้และสร้าง plan_context โดยอัตโนมัติหากผู้ใช้กำลังดูแปลงนาอยู่ plan_context เป็นข้อความสรุปสถานการณ์จริงของแปลงนา ประกอบด้วยพันธุ์ข้าว วิธีปลูก พื้นที่ ประเภทดิน จำนวนวันที่ผ่านมา ระยะการเจริญเติบโตปัจจุบัน งานวันนี้ และงานที่จะมาถึงใน 7 วัน นอกจากนี้ยังรวบรวม history จาก messages ก่อนหน้า 6 รายการในหน้าต่างแชท และระบุ collection ด้วยค่า plan.varietyId ฝั่ง frontend ซึ่งถูก map ให้เป็น collection_name แล้ว จากนั้นส่ง HTTP POST ไปยัง /chat/ พร้อม JWT token ใน Authorization header

ขั้นตอนที่ 2 — ตรวจสอบสิทธิ์และรับ Request: FastAPI route POST /chat/ รับ request โดย get_optional_user() dependency พยายามถอดรหัส JWT token หากมี token ที่ถูกต้อง จะได้ current_user object สำหรับบันทึก history ภายหลัง หากไม่มี token หรือ token หมดอายุ current_user จะเป็น None และระบบยังคงตอบคำถามได้ แต่จะไม่บันทึกประวัติการสนทนา

ขั้นตอนที่ 3 — แปลงคำถามเป็น Vector และค้นหา Chunks: rag_service.ask_question() จับเวลาเริ่มต้นแล้วส่งคำถามไปยัง _search() ซึ่งเรียก Gemini Embedding API เพื่อแปลงคำถามเป็น vector embedding จากนั้นค้นหาใน ChromaDB ด้วยอัลกอริทึม Maximal Marginal Relevance (MMR) โดยกำหนด fetch_k=10 คือดึง 10 candidates มาก่อน แล้วคัดเลือก k=3 chunks ต่อ collection ที่มีทั้งความเกี่ยวข้องกับคำถามสูงและมีเนื้อหาหลากหลายไม่ซ้ำซ้อนกัน MMR จึงให้ผลดีกว่า similarity search ธรรมดาในกรณีที่หลาย chunks มีเนื้อหาใกล้เคียงกัน การเลือก collection ที่จะค้นหาขึ้นอยู่กับ request หากระบุ collection จะค้นใน collection นั้นและ general เสมอ หากไม่ระบุจะค้นทุก collection ที่โหลดไว้ตอน startup

ขั้นตอนที่ 4 — รวม Context และสร้าง Prompt: ระบบประกอบ context จาก 3 แหล่งตามลำดับความสำคัญ ได้แก่ (1) plan_context ซึ่งวางไว้ก่อนเพื่อให้ LLM รับรู้สถานการณ์จริงของผู้ใช้ก่อนอ่านเอกสาร (2) เนื้อหาของ chunks จาก ChromaDB ที่ต่อกันด้วยตัวคั่น และ (3) ประวัติการสนทนา 10 รายการล่าสุดที่สร้างผ่าน _build_history_text() เพื่อให้ LLM รักษาบริบทการสนทนาต่อเนื่องได้ LangChain PromptTemplate นำ context ทั้งหมดมาสร้างเป็น prompt สมบูรณ์ โดยกำหนดให้ตอบจาก Context เป็นหลัก ตอบภาษาไทยไม่เกิน 5 ประโยค หากไม่มีคำตอบตรงให้ตอบคำแนะนำทั่วไปได้แต่ต้องมีหมายเหตุ และห้ามแต่งตัวเลขเฉพาะที่ไม่มีในเอกสาร

ขั้นตอนที่ 5 — เรียก LLM และประมวลผลคำตอบ: LangChain ส่ง prompt ไปยัง Gemini 2.5 Flash ผ่าน ChatGoogleGenerativeAI โดยกำหนด temperature=0.3 เพื่อลดความสุ่มและลด hallucination Gemini ตอบกลับเป็น AIMessage object ระบบดึง raw.content ซึ่งเป็นข้อความคำตอบ จากนั้นลบ Markdown syntax (**) ออกด้วย regular expression เนื่องจาก Gemini มักแทรก bold formatting ซึ่ง FloatingChat ไม่ได้ render Markdown นอกจากนี้ยังดึง usage_metadata เพื่อบันทึกจำนวน input และ output tokens

ขั้นตอนที่ 6 — บันทึก Log และส่งคำตอบกลับ: ระบบคำนวณ response_time_ms จากเวลาที่ใช้ทั้งหมดตั้งแต่เริ่ม request จากนั้นตรวจสอบ current_user หากผู้ใช้ล็อกอิน ระบบจะ INSERT record ลงตาราง chat_history พร้อม metrics ได้แก่ model_used, embedding_model, retrieval_strategy, chunk_size, retrieval_k, chunks_retrieved, input_tokens, output_tokens และ response_time_ms ข้อมูลเหล่านี้ใช้สำหรับการทดลองประเมินประสิทธิภาพระบบ RAG สุดท้ายส่ง ChatResponse เป็น JSON กลับไปยัง Frontend ซึ่ง FloatingChat จะแสดงคำตอบและชื่อเอกสารอ้างอิงทันที

3.4.4 ระบบจัดการเนื้อหาและตรวจจับช่องว่างความรู้ (Admin CMS และ Gap Detector)

นอกเหนือจากการอัปโหลดเอกสารใน Phase 1 ระบบยังมีกลไกวิเคราะห์คุณภาพฐานความรู้อย่างต่อเนื่องผ่าน Gap Detector endpoint GET /admin/gaps ซึ่ง Query จากตาราง chat_history ใน PostgreSQL เพื่อค้นหา 20 คำถามที่ตรงเงื่อนไขดังนี้

  • คำถามที่มี chunks_retrieved = 0 หมายความว่า request นั้นไม่มี chunk จากฐานความรู้ถูกนำมาใช้ อาจเกิดจาก MMR search ไม่พบเนื้อหาที่เกี่ยวข้อง หรือเป็นการตอบผ่านโหมด No-RAG ซึ่งมีความเสี่ยงต่อการตอบโดยไม่อ้างอิงเอกสาร
  • คำถามที่คำตอบ (answer field) มีคำว่า "ไม่ทราบ" ตามเงื่อนไข endpoint ปัจจุบัน บ่งชี้ว่าฐานความรู้อาจยังไม่ครอบคลุม ทั้งนี้ prompt ล่าสุดยังมีหมายเหตุสำหรับกรณีที่ใช้ความรู้ทั่วไปเมื่อไม่พบคำตอบตรงในเอกสาร

ผลลัพธ์ช่วยให้ Admin ทราบหัวข้อที่ขาดเอกสารรองรับและควรอัปโหลดเพิ่มเติม กระบวนการปิดช่องว่างความรู้จึงเป็นวงจรต่อเนื่อง ได้แก่ ผู้ใช้ถามคำถาม → บันทึก metrics ลง PostgreSQL → Admin ตรวจ Gap Detector → อัปโหลดเอกสารใหม่เข้า ChromaDB → RAG ตอบได้ดีขึ้นในการถามครั้งต่อไป

สำหรับการลบเอกสาร endpoint DELETE /documents/{id} จะดำเนินการ 3 ขั้นตอนพร้อมกัน ได้แก่ ลบทุก chunk ที่มี metadata.source ตรงกับ file path ออกจาก ChromaDB ผ่าน vs._collection.delete(where={"source": file_path}) ลบไฟล์ต้นฉบับออกจากดิสก์ และลบ record ออกจากตาราง documents ใน PostgreSQL

3.4.5 ระบบจัดการพันธุ์ข้าว (Variety Management)

ระบบจัดการพันธุ์ข้าวเป็นศูนย์กลางของข้อมูลเกษตรกรรมในระบบ เนื่องจากตาราง rice_varieties ส่งผลต่อทั้งระบบสร้างแผนปลูก (ค่า tillering_day, heading_day, สูตรปุ๋ย) และระบบ RAG (collection_name ใช้เป็นชื่อ ChromaDB collection) การอ่านรายการพันธุ์ข้าวผ่าน GET /varieties/ เป็น public endpoint และคืนเฉพาะพันธุ์ที่ is_active=true ส่วนการสร้าง แก้ไข ดูสถิติ และลบพันธุ์ข้าวจำกัดเฉพาะ Admin ผ่าน require_admin

การสร้างพันธุ์ข้าวใหม่ (Create): Frontend ส่ง HTTP POST ไปยัง /varieties/ พร้อม JSON body ที่ประกอบด้วยข้อมูลครบถ้วน ได้แก่ ชื่อพันธุ์ (name), ชื่อ collection (collection_name), อายุเก็บเกี่ยว (harvest_age_days), ค่าระยะการเจริญเติบโต (tillering_day, panicle_initiation_day, heading_day), อัตราและสูตรปุ๋ยครั้งที่ 1/2 (fert1_rate, fert2_rate, fert1_formula, fert2_formula) Backend ตรวจสอบว่า collection_name เป็นตัวพิมพ์เล็กและไม่มีช่องว่าง ไม่ซ้ำกับที่มีอยู่ในระบบ และตรวจลำดับระยะเจริญเติบโตให้เป็น tillering_day < panicle_initiation_day < heading_day < harvest_age_days เพื่อป้องกันแผนผิดจากข้อมูลตั้งต้น หลังจาก INSERT record ลง PostgreSQL สำเร็จ ระบบเรียก rag_service.load_collections([collection_name]) ทันทีเพื่อสร้าง ChromaDB collection ใหม่และเพิ่มเข้า vectorstores dict โดยไม่ต้อง restart server collection ใหม่นี้พร้อมรับเอกสารได้ทันที

การแก้ไขพันธุ์ข้าว (Update): Frontend ส่ง HTTP PUT ไปยัง /varieties/{variety_id} โดยส่งเฉพาะ field ที่ต้องการแก้ไข (partial update ด้วย exclude_unset=True) Backend วนลูป field ที่ส่งมาและ setattr ลงบน ORM object โดยตรง ทั้งนี้ collection_name ไม่สามารถแก้ไขได้หลังสร้างแล้ว เนื่องจากจะทำให้ ChromaDB collection และเอกสารที่ผูกอยู่สูญหายการเชื่อมโยง การแก้ไขค่าระยะการเจริญเติบโตหรือสูตรปุ๋ยจะมีผลกับแผนที่สร้างใหม่เท่านั้น แผนที่มีอยู่แล้วไม่ได้รับผลกระทบเนื่องจากใช้ resources_snapshot ที่บันทึกไว้ตั้งแต่ตอนสร้าง

การลบพันธุ์ข้าว (Delete): การลบพันธุ์ข้าวเป็นการดำเนินการที่มีผลกระทบกว้างที่สุดในระบบ endpoint DELETE /varieties/{variety_id} จะดำเนินการตามลำดับดังนี้ ประการแรก Query ตาราง documents เพื่อหาเอกสารทั้งหมดที่ผูกกับ collection_name นั้น ประการที่สอง วนลูปเอกสารแต่ละชิ้นเพื่อลบไฟล์ออกจากดิสก์และลบ chunks ออกจาก ChromaDB ผ่าน rag_service.delete_document() ประการที่สาม ลบ record ของเอกสารออกจากตาราง documents ประการที่สี่ ลบโฟลเดอร์ ./uploads/{collection}/ ออกจากดิสก์ด้วย shutil.rmtree() ประการที่ห้า ลบ record ของพันธุ์ข้าวออกจากตาราง rice_varieties และ commit ทั้งหมด ทั้งนี้แผนการปลูกที่มีอยู่แล้วจะยังคงทำงานได้เนื่องจากบันทึก variety_name ไว้เป็น snapshot แต่จะไม่สามารถสร้างแผนใหม่ด้วยพันธุ์ที่ลบไปแล้วได้อีก

การดูสถิติพันธุ์ข้าว (Stats): endpoint GET /varieties/{variety_id}/stats คืนค่า doc_count ซึ่งนับจำนวนเอกสารใน PostgreSQL ที่ผูกกับ collection นั้น ใช้แสดงใน Admin Panel เพื่อให้ Admin ทราบว่าพันธุ์ใดมีเอกสารสนับสนุนเพียงพอสำหรับ RAG แล้วหรือยัง
